# Implementation

Apply this when writing or extending Playwright tests. The E2E contract, linked from the skill, governs execution, oracles, test quality, and status words; this file adds how to write the code. Short code patterns are in [examples](examples.md); adapt them to the repo's existing style.

- Use verified user-facing locators (`getByRole`, `getByLabel`) or explicit test IDs. Scope and use exact matching where needed. CSS is acceptable when evidenced and stable. Do not use arbitrary `first()` or `nth()` to hide an ambiguous match.
- Use web-first assertions and observable readiness. Pair important actions with their specified outcomes. Preserve each meaningful expected result. Avoid fixed sleeps, `networkidle` waits, force clicks, swallowed errors, and conditional assertions that turn missing behavior into a pass.
- Make every negative assertion able to fail without depending on data the test does not own: watch the requests the page sends, or query only records created during this test or carrying its unique data. A before/after comparison around a test that did nothing is not evidence, and "no booking for Ben exists" fails in an environment with history.
- Keep one coherent journey in one test, with `test.step` per case step where it helps. Give independent scenarios their own starting state. Include the case ID in the test title, and add a tag such as `{ tag: "@BK-01" }` when the repo uses tags. Parameterize only when each outcome stays traceable.
- Reuse the fixtures, helpers, page objects, API clients, and data factories found in the inventory step. Import them the way nearby tests do. Extend an existing one instead of writing a parallel version. Add a page or component object only when actual reuse justifies it, in the folder the repo already uses. Do not restructure the suite for a small addition.
- Isolate backend records as well as browser storage. Register each created record with a fixture as soon as its ID is known, and delete it in fixture teardown so cleanup also runs when an assertion fails. Teardown attempts every record newest first and reports all failures together. Clean up only records the run created. Generate unique names from `testInfo` or a timestamp when parallel workers could collide.
- Authenticate through a setup project that performs a real UI login and saves `storageState`, one file per role, kept out of version control. Shared auth is suitable only when tests do not interfere with each other's server state. Keep a real login flow for login cases.
- When a valid assertion exposes an application defect, keep the assertion and leave the test failing by default. Use `test.fail()` with an annotation linking the defect only when project policy or the user allows expected failures, verify after each run that the failure message is that defect, and report it as `expected-fail`, never as passed. Never use `test.skip` or a weakened expectation instead.
- Retain existing browser projects and CI behavior. Add only necessary configuration. For a new suite, start with one supported browser and `forbidOnly: !!process.env.CI`. Parallelize after account and data isolation is established. Read the installed version's help before adopting an unfamiliar API.
